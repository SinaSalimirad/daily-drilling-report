# 03 — Database Schema and Migrations

PostgreSQL, Drizzle ORM, `pg` driver, drizzle-kit. The entity diagram is in section 13 of `DMR_Workbook_Analysis.md`; this document fixes the rules.

## Conventions

| Topic | Rule |
|---|---|
| Names | `snake_case`; tables plural (`daily_reports`); foreign keys `<table_singular>_id` |
| Primary key | `id uuid primary key default gen_random_uuid()` |
| Timestamps | `created_at`, `updated_at` as `timestamptz not null default now()` |
| Authorship | `created_by`, `updated_by` as nullable `uuid` from the first migration; the foreign key to the user table is added in v0.9.0 |
| Deleting | Master data is archived (`archived_at`), not deleted, once a report refers to it. Daily rows are deleted with their report (`on delete cascade`) |
| Closed lists | `pgEnum` (report status, pit type, product unit, section type) |
| Open lists | Lookup tables (activities, mud types, sample sources) so they can grow without a migration |
| Money and stock quantities | `numeric(14,3)` for quantities, `numeric(14,2)` for money |
| Measurements | `double precision` |
| Report date | `date`. Everything else that is a moment in time: `timestamptz` (UTC) |
| JSON | `jsonb` only for result snapshots, unit preferences and template-specific sample properties |

## Units at rest (SI)

| Quantity | Stored unit | Workbook unit |
|---|---|---|
| Depth, length | m | m, ft |
| Diameter, cake thickness | m | in, 1/32 in |
| Volume | m³ | bbl |
| Density (mud weight) | kg/m³ | PCF, ppg, SG |
| Pressure, yield point, gel strength | Pa | psi, lb/100 ft² |
| Flow rate | m³/s | gal/min |
| Plastic viscosity | Pa·s | cP |
| Concentration, chlorides, hardness | kg/m³ | lb/bbl, mg/L |
| Mass | kg | kg, MT, lb |
| Rate of penetration | m/s | m/hr |
| Temperature | °C | °F |
| Durations (activities, equipment) | hours | hours |
| Dial readings, percentages, pH | dimensionless | same |
| Funnel viscosity | seconds (Marsh funnel, per quart) | sec/qt |

Accepted non-SI exceptions: °C, hours, percent. A product's **package** (`25 kg`, `55 gal`) is catalogue data and keeps its own unit; inventory quantities are counts of packages.

The display unit system is a setting of the project (`projects.unit_system jsonb`), default SI, with a preset that matches the workbook (bbl, PCF, psi, m, gal/min, lb/bbl, °F).

## Key constraints

- `daily_reports`: `unique (well_id, report_no)` and `unique (well_id, report_date)`.
- `daily_reports.status`: `draft` | `submitted`. `revision int not null default 1`, `submitted_at`.
- `project_products`: `unique (project_id, product_id)`.
- `inventory_moves`: `unique (report_id, project_product_id)`; `unit_price` copied onto the row.
- `pit_readings`: `unique (report_id, pit_id)`; `volume <= pits.capacity` (checked in the service).
- `volume_entries`: `unique (report_id, item)`; `item` is an enum of **input** items only.
- `mud_samples`: `unique (report_id, seq)`.
- `survey_stations`: `unique (well_id, measured_depth)`.
- `report_results`: primary key `report_id`; columns `revision`, `engine_version`, `is_stale boolean`, `payload jsonb`.

## Never stored

Stock, section / monthly / cumulative totals, start volume, built volume, total losses, end volume, cumulative equipment hours, report cost. They are queries. The only stored calculation is `report_results`.

## Editing a submitted report

1. The update must carry the `revision` the client read. A mismatch is rejected (`409 REVISION_MISMATCH`).
2. In one transaction: write the change, `revision = revision + 1`, rewrite this report's `report_results`, set `is_stale = true` on the results of every later report of the same well.
3. Stale results are recalculated in report order (after the transaction, or on first read).
4. From v0.9.0 the change is written to `audit_log` (who, when, before / after).

## Migration workflow

1. Change the Drizzle schema in `apps/api/src/db/schema/`.
2. `bun run db:generate` → drizzle-kit writes a SQL file in `migrations/`.
3. **Read the SQL.** Rename it to say what it does if the generated name is meaningless. Delete every `"public".` that drizzle-kit puts in front of enum types and foreign-key targets: the tests apply migrations to a schema of their own (`apps/api/src/test/db.ts`), and `src/db/migrations.test.ts` fails while a migration names `public`.
4. `bun run db:migrate` locally.
5. Commit schema change and migration **in the same pull request**.

Rules:

- A migration that has reached `main` is never edited. Fix forward with a new one.
- `drizzle-kit push` is for throwaway local experiments only, never for shared databases.
- Migrations must be backward compatible with the previous release of the API (add first, remove one release later), so a rollback of the code does not need a rollback of the data.
- Production migrations run in the deploy job, before the new API starts.

## Seed data

- `db:seed:lookups` — activities, sample sources, mud types, section types. Runs in every environment and is idempotent.
- `db:seed:demo` — the well from the analysed workbook (PYW-24ST1, report 1). Local and test only. It is also the fixture for integration tests.
