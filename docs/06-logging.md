# 06 — Logging

Goal: for any failed request, find out what happened from the `requestId` alone.

## Tools

- **API**: logixlysia as the Elysia logging plugin (request logs and the app logger). Check option names against its documentation when wiring it in v0.1.0.
- **Nginx**: access and error logs. The access log is one JSON line per request: `time`, `source: "nginx"`, `requestId`, `method`, `path`, `status`, `durationS` (seconds, millisecond resolution — Nginx's `$request_time`), `upstream`, `bytes`.
- **Output**: stdout / stderr only. Docker collects it. No log files are written by the application.

## Format

| Environment | Format |
|---|---|
| Development | Coloured, human-readable lines |
| Production | One JSON object per line |

Fields of a request log line:

| Field | Note |
|---|---|
| `time` | ISO 8601 UTC |
| `level` | see below |
| `requestId` | from `X-Request-Id` (set by Nginx) or generated by the API |
| `method`, `path` | path pattern, not the raw URL with IDs when available |
| `status`, `durationMs` | |
| `userId` | from v0.9.0 |
| `errorCode` | for failed requests |

## Request ID

1. Nginx sets `X-Request-Id` (`$request_id`) and logs it.
2. The API reuses it or generates a UUID, attaches it to every log line of the request, returns it in the `X-Request-Id` response header and in every error body.
3. The frontend shows it in the error toast, so a user can report it.

## Levels

| Level | Use | Examples |
|---|---|---|
| `error` | A bug or a failed dependency. Needs attention | Unhandled exception, database unreachable, migration failed |
| `warn` | Handled, but unusual | 4xx responses, slow query (> 1 s), stale result recalculation retried |
| `info` | Normal milestones | Server start, request completed, domain events |
| `debug` | Development detail | SQL text, calculation inputs. Off in production |

`LOG_LEVEL` sets the threshold (`info` in production).

## Domain events (level `info`)

Logged by services after the transaction commits, as `event` plus IDs:

- `report.created`, `report.submitted`, `report.edited_after_submit`, `report.deleted`
- `report.warnings_acknowledged` (with the warning codes)
- `results.recalculated` (well, number of reports)
- `master.archived` (table, id)
- `auth.sign_in`, `auth.sign_in_failed`, `auth.sign_out` (from v0.9.0)

## Never logged

- Passwords, session tokens, cookies, `Authorization` and `Cookie` headers.
- Full request or response bodies. Log IDs and counts instead.
- Database connection strings and other secrets.
- Personal data beyond the user ID.

## Errors

- 4xx: one `warn` line with `errorCode`; no stack.
- 5xx: one `error` line with `errorCode`, message and stack.
- An error is logged **once**, in the error handler. Code that rethrows does not log.

## Application log is not the audit log

| | Application log | Audit log |
|---|---|---|
| Purpose | Operating and debugging | Who changed which business record |
| Store | stdout, rotated | `audit_log` table |
| Kept | Days to weeks | As long as the data |
| Since | v0.1.0 | v0.9.0 |

## Retention

Docker `json-file` driver with `max-size: 10m` and `max-file: 5` per container. Nginx logs rotate through the container's stdout the same way. Shipping logs to an external system is out of scope until there is a need.

## Frontend

- `console` output only in development.
- Unhandled errors are caught by error boundaries and shown; they are not sent anywhere yet. An error-reporting service can be added after v1.0.0.
